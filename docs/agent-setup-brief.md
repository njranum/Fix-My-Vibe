# Fix My Vibe — Agent Setup Brief

## Purpose

This document describes the role of each agent in the Fix My Vibe multi-agent pipeline,
what inputs it receives, what tools it uses, and what it produces.

All agents run on Azure AI Foundry using o4-mini. Each agent is created fresh per run,
given tool definitions, and deleted after completing. The model decides which tools to
call — Python only executes them and returns results.

---

## Agent Roles

### Scanner Agent (`src/agents/scanner.py`)

**Role:** Filesystem detective — detects AI tools, stack, and security issues.

**Input:** `project_path` (string)

**Tools (model decides which to call):**
- `scan_directory` — config file signatures (Layer 1), stack detection, security scan
- `check_path_tools` — PATH / shutil.which (Layer 2)
- `check_vscode_extensions` — .vscode/extensions.json (Layer 3)
- `read_existing_context_file` — audit existing configs for quality issues
- `infer_project_conventions` — detect test/build/lint commands, README summary

**Output:** Structured ScanResult JSON with `detected_tools`, `detected_stack`,
`security_issues`, `missing_configs`, `existing_configs`, `conventions`.

**Why agentic:** The model may skip `check_vscode_extensions` if no `.vscode/` exists,
or call `read_existing_context_file` only when it finds existing AI config files.

---

### Researcher Agent (`src/agents/researcher.py`)

**Role:** Best-practice knowledge retrieval via Tavily web search.

**Input:** ScanResult (detected tools + stack)

**Tools (model decides queries):**
- `search_web` (Tavily API) — model generates its own queries based on what was found

**Output:** Per-tool research with `recommended_sections`, `security_notes`,
`best_practices`, `source_urls`.

**Why agentic:** The model decides what to search for. A project with exposed `.env` and
Cursor detected will prompt different queries than a clean project.

**Local fallback:** Static knowledge base (no Tavily required in `--local` mode).

---

### Planner Agent (`src/agents/planner.py`)

**Role:** Pure reasoning — gap analysis and config file content generation.

**Input:** ScanResult + ResearchResult

**Tools:** None (reasoning only)

**Output:** ActionPlan JSON with ranked actions. Each action includes the **actual file
content** to write, generated by o4-mini for this specific project — not a template.

**Why agentic / why this matters:** The Planner is where project-specific reasoning
produces project-specific output. Given a FastAPI project with pytest and a README
describing a user management API, the generated CLAUDE.md will reference those specifics.
Two different projects produce two different CLAUDE.md files. The model reads the
conventions, reads the research, and writes real content.

**Safety:** Planner produces the plan — it does not write files. The Executor only runs
after user confirmation.

---

### Executor Agent (`src/agents/executor.py`)

**Role:** File writer with mandatory user confirmation gate.

**Input:** ActionPlan + `project_path` + confirmed action ranks (after user approval)

**Tools:**
- `write_file` — writes file with automatic backup if target exists

**Safety rules (non-negotiable):**
- Confirmation gate runs in Python before the agent is created — user sees the plan first
- Agent only receives the ranks the user approved
- Backs up existing files as `.bak` before overwriting

**Output:** ExecutionResult with written/skipped/error counts.

---

### Verifier Agent (`src/agents/verifier.py`)

**Role:** Quality gate — verifies written files are actually useful, not just present.

**Input:** ExecutionResult + ActionPlan + `project_path`

**Tools:**
- `verify_file` — checks file exists and contains expected sections
- `read_existing_context_file` — reads content for quality assessment

**Output:** VerificationResult with pass/fail per file, quality concerns, and
recommendations. Includes a `QUALITY` rating: excellent / good / acceptable / needs_work.

**Why agentic:** The model makes qualitative judgments. It can flag a CLAUDE.md that
passes structural checks but is still generic boilerplate, or a .cursorrules that is
technically present but too short to guide an AI assistant meaningfully.

## Data Flow

```
User input (project_path)
        │
        ▼
    Scanner ──────────────────────────────► ScanResult
                                                │
                                                ▼
                                        Researcher ──────────► ResearchResult
                                                │
                                                ▼
                                        Planner ─────────────► ActionPlan
                                                │              (with file content)
                                ┌───────────────┘
                                │
                                ▼
                    [User Confirmation Gate]
                    "Apply all / select / cancel"
                                │
                                ▼
                            Executor ────────────────────► ExecutionResult
                                │
                                ▼
                            Verifier ────────────────────► VerificationResult
                                │
                                ▼
                        Final report to user
```

## Local vs Foundry Mode

| | Local (`--local`) | Foundry (default) |
|-|-------------------|-------------------|
| Model | None | o4-mini via Agents API |
| Tool execution | Python decides what to call | Model decides what to call |
| File content | Python templates | Model-generated, project-specific |
| Speed | ~3 seconds | ~2-4 minutes |
| Use case | Development, testing | Real use, demo, submission |

Both modes produce the same output structure. The `run()` method is local; `run_with_foundry()` is agentic.
